## [未发布 / Model Studio 双能力自动选型收口] - 2026-08-14

### 修改

- 独立审查发现百炼 ASR 候选卡仍将 `paraformer-v2` 预填给 Renderer，并可绕过目录 proof 保存。`SUP-006e` 现覆盖 `asr`、文本语义分析与视频理解复核三项能力：普通用户始终只填写 API 密钥，三条 Model Studio 路径均由主进程自动选择兼容模型；本轮不启用新的百炼 ASR 执行器。
- 同一审查还确认 ASR 仅有保存时自动发现、没有可操作的检测入口。ASR 选中 Model Studio 时现与另两项能力一致提供“检测并自动选择”；该入口只读取受限模型目录并显示脱敏结果，和腾讯云签名检测按供应商互斥显示。

- 补齐 `SUP-006e` 与 `AC-SUP-005b`：Model Studio 的文本语义分析和视频理解复核共用受控自动选型路径，模型输入只读；检测与保存均按当前能力发现模型，不能持久化手填模型 ID。
- 目录模型更新为 2026-08-14 官方中文视觉文档明确列出的 `qwen3.7-flash`、`qwen3.6-flash`、`qwen3.7-plus`、`qwen3.6-plus` 优先级，不再使用过时的 Qwen3-VL 名称。
- 历史空值或“请按开通模型填写”统一显示“等待自动选择”；能力门禁不再提示用户填写实际模型，而是提示检查 API 密钥和账户开通状态。
- 独立审查发现 allowlist 名称本身不能证明它来自当前账号的模型目录：保存 IPC 现改为只接受主进程发现成功后签发的一次性、短时且密钥绑定的选型凭证，避免 Renderer 直接提交 allowlist 模型名绕过账号开通校验。

### 状态

- 此项只收口配置保存、兼容模型目录和受控错误态。`pnpm test`、typecheck、build 与隔离 Electron E2E 已在当前树通过；`audit:fidelity` 仍为 `completed=0, incomplete=94`，帧级视频复核、真实候选资格和 Phase 17–20 完成均未获此改动证明。

## [未发布 / Version 48 原剧切片既有预览差异复核] - 2026-08-14

### 结论

- 对 `screen-clip:candidate-selected`、`screen-clip-pool:default`、`screen-clip-report:default` 的既有 1440×900 项目库/Electron 配对建立了独立迁移卡：`docs/prototype-migration/original-clip-v48-project-preview-delta-20260814.md`。

### 后续

## [未发布 / Phase 18 帧级视频复核受控验收] - 2026-08-14

### 修改

- 新增仅供打包身份显式调用的帧级 provider 能力验收入口：只接受冻结公开 `dev-04`、绝对 Baseline v1 manifest 与媒体 SHA-256，读取全帧 PTS 后仅提取中点附近不超过 12 张 JPEG 帧。生产 profile 和加密密钥仅以只读源库复制至临时 SQLite；外发仅含临时 UUID evidence ID、受控 prompt 与 JPEG data URL，不包含字幕、候选、剧集/媒体路径、PTS、整段视频或 provider 原文。
- 验收摘要以新建绝对 JSON 路径的 `wx` 方式不可覆盖写入；成功只允许记录样本 ID、媒体 SHA-256、帧数、`supported` 与生产库写入 0，失败只允许固定 reason/code、耗时与生产库写入 0。无论结果如何，都不得由此创建视觉场景卡、`qualified` 候选、导出或 Phase 完成结论。
- OpenAI-compatible 视频适配器仅在 HTTP 400 响应的 `error.message`、`error.code` 或 `error.param` 明确拒绝 `response_format` 时，才去掉该字段重试一次；其余 400 不重发 JPEG 帧，且响应继续仅接受完整 JSON 或完整 Markdown JSON 代码块。

### 验收状态

- 计划：将打包身份的受控真实验收运行目录与只读配置来源显式分离。验收进程可使用新建隔离用户目录，同时仅从指定的既有用户目录只读复制 provider profile 与加密密钥引用；不得迁移、写入、删除或输出来源目录中的任何数据。该调整只解决已运行旧 EXE 占用同一应用运行通道导致的无结果退出，不改变公开样本、外发最小化、资格或视觉门禁。
- 实现：`v0.1.86` 的**帧级视频验收入口**要求显式 CLI 同时提供两个不同的绝对目录：隔离运行目录与只读配置来源目录；缺失、相对路径、同一路径、嵌套目录或 junction/symlink 别名一律拒绝，杜绝回退生产目录。该规则不改变尚未接入只读来源复制的 ASR、文本语义或连通性探针入口。定向回归、类型检查和差异检查已通过，仍需独立复审及新 verification EXE 的公开 `dev-04` 实跑。该验收不能读取或外发 hidden-01，也不能把 provider 成功扩大为视觉场景卡或 Phase 完成。
- 运行时修正计划：实际 `v0.1.86` 隔离运行复验产生固定 `missing-key`，而同一打包身份、原用户数据上下文的最小 probe 曾可解密并连通。根因是 Windows 受保护密钥与 Electron 当前用户数据上下文绑定，切换 `userData` 会使已保存的加密密钥无法解密；这不是密钥丢失。帧级入口改为显式使用既有应用身份的只读配置来源，仅以临时 SQLite 承载 profile/密钥副本和所有验收写入；不再要求切换 Electron `userData`，避免破坏安全存储上下文。原用户 SQLite 仍只读打开，验收结束后临时 SQLite 清理，结果继续 `wx` 不可覆盖。
- 实现：版本递增为 `v0.1.87`，已移除会改变 Electron 密钥保护上下文的运行目录替换；帧级验收以当前打包身份默认用户目录（或显式绝对只读来源目录）只读打开配置库，并只向临时 SQLite 写入副本。定向回归、类型检查、差异检查和独立审查后才允许重新打 verification-only 包。先前 `v0.1.86` 的 `missing-key` 摘要是无效隔离方式的诊断记录，不构成供应商或场景卡结论。
- 打包空间整改计划：D 盘不足以再次构建约 700 MiB 的本地 OCR runtime，但本轮 main-process 改动未涉及 OCR 代码或模型。打包脚本将仅在当前 `tools/local-ocr/runtime` 与最近已成功生成的 verification 包 runtime 逐文件 SHA-256 一致、且当前 runtime `--self-test` 通过时复用该运行时；任一文件不一致、参考包缺失或自检失败均拒绝打包，不得用旧 EXE、旧 `out` 或未验证缓存替代。
- `v0.1.85` 对冻结 `dev-04` 的真实验收仍为受控 `provider-failed`（73,701 ms、生产库写入 0），不表示密钥丢失。只读配置检查确认 profile、端点与密钥引用均存在，但当前模型不带视觉模型标识；后续需选择可用视觉模型后使用新 verification 包重跑。
- Phase 19 真实导出与治理证据已在冻结 Baseline 与临时 SQLite 下复跑：实际 `dev-06` FFmpeg/ffprobe 导出边界、`dev-05/dev-06/hidden-02` 恢复与指纹阻断、6+2 PTS 证据包共 3 文件 / 3 测试通过；不写生产 SQLite、源媒体或用户资产。该通过不能替代 hidden-01 跨窗、视频复核、候选资格或视觉门禁。
- 当前源码构建后的 Phase 20 隔离 Electron 回归 2 文件 / 2 测试通过：V49 监视器、审阅范围、双时间线、0.1 秒微调、确认、候选池导出/报告及 1440×900、1280×720 无横向溢出均已复验；视觉保真审计仍未通过，因此继续标记 `visual-unverified`。
- 当前全量回归基线：`pnpm test` 102 文件 / 550 通过 / 5 显式跳过，typecheck、设计合同、差异检查通过，Electron E2E 为 15 通过 / 8 显式跳过；`audit:fidelity` 仍为 `completed=0, incomplete=94`。跳过的真实媒体与打包 DPI 条件不计为完成证据，产品继续不是正式候选或发布物。
- Open Design v0.19.0 daemon 已以显式 workspace 上下文只读验证可访问当前项目；其项目库缺少合同要求的全量逐状态双视口预览，不能以已有 V49 `unmerged-pending-confirmation` 附件、历史 PNG 或本地 HTML 充数。创建独立待确认状态基线附件的设计运行因 `AMR_INSUFFICIENT_BALANCE` 在产物生成前失败（0 新文件）；该外部额度问题不影响本地实现，但在补足并确认项目库状态设计前，视觉保真与正式完成继续阻断。

## [未发布 / Phase 18 真实语义候选请求上限] - 2026-08-13

### 修改

- 文本语义 provider 的受限输出合同新增由应用持有的 `maxSelections`：模型仍可读取本轮冻结的全部语义窗口和完整相邻上下文，但只允许返回用户本轮请求数量以内的最优候选及其必需叙事事件。
- 该上限不改变证据 ID 白名单、起止时间顺序、跨窗连续性、A/B 级资格、视频复核、候选去重或发布门禁；模型多返回、缺必需事件或引用窗口外 ID 仍只允许一次修复，随后阻断。

### 原因与验收

- `dev-02` 在真实 OCR、腾讯 ASR 和 DeepSeek 连通后拥有 44 个可分析窗口，但用户只请求 1 条候选。此前请求隐式要求模型为每个窗口都生成完整事件和候选，真实运行在严格结构化校验阶段受控失败（`provider-response-invalid`）。本调整只消除与用户请求不一致的冗余输出压力，不把失败结果解释为密钥、网络或候选资格问题。
